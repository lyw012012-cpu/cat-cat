# 스파이크 #1 — 활성 창 감지 / URL 추출 / 규칙 판정

이 스파이크의 목적은 **동작하는 앱을 만드는 게 아니라 "된다/안 된다"를 알아내는 것**입니다.
결과가 나오면 이 폴더는 버려도 됩니다. 남는 건 아래 체크리스트의 답입니다.

---

## 1. 무엇을 확인하려는가

| #   | 질문                        | 안 되면 생기는 일            |
| --- | ------------------------- | --------------------- |
| Q1  | 지금 사용자가 보는 창이 뭔지 알 수 있는가  | 앱 전체가 성립하지 않음         |
| Q2  | 그게 **유튜브 쇼츠인지** 구분할 수 있는가 | 대표 기능을 바꿔야 함          |
| Q3  | 그 창을 닫을 수 있는가             | `close` 대신 `warn`만 가능 |

Q1은 거의 확실히 됩니다. **Q2와 Q3가 진짜 관문입니다.**

---

## 2. 실행

```bash
# (1) 아무 OS에서나 — 로직만 검증. Windows 없이도 됩니다
python watch.py --simulate
python test_rules.py

# (2) Windows에서 — 실제 감지
pip install uiautomation      # URL 추출용. 없어도 창 제목까지는 나옵니다
python watch.py

# (3) 실제로 창을 닫아봅니다 (작업 저장하고 실행하세요)
python watch.py --action close
```

옵션: `--interval 0.5` 관찰 주기, `--out log.jsonl` 기록 파일.

---

## 3. Windows에서 직접 확인할 것 (여기가 본편)

실행해 놓고 아래를 하나씩 해보면서 **콘솔에 뭐가 찍히는지 적어두세요.**

### Q2 — 쇼츠 구분

- [ ] 크롬에서 유튜브 **일반 영상**을 연다 → `URL :` 줄에 `youtube.com/watch?v=...` 가 뜨는가
- [ ] 크롬에서 **쇼츠**를 연다 → `youtube.com/shorts/...` 로 바뀌는가, 그리고 `★ 규칙 발동` 이 뜨는가
- [ ] 쇼츠를 위아래로 넘겨본다 → URL이 따라 바뀌는가, 아니면 처음 것에서 멈춰 있는가
- [ ] **탭 여러 개**를 띄우고 다른 탭으로 전환 → 활성 탭의 URL로 바뀌는가
- [ ] 시크릿 창에서도 되는가
- [ ] 엣지/웨일에서도 되는가
- [ ] URL 한 번 읽는 데 얼마나 걸리는가 (콘솔이 버벅이면 느린 것)
- [ ] `[url] 추출 실패` 가 뜬다면 **어떤 예외인지 그대로 적어두기**

> **핵심:** 창 제목은 일반 영상이든 쇼츠든 `"제목 - YouTube - Chrome"` 으로 똑같습니다.
> 그래서 UI Automation으로 주소창 값을 직접 읽습니다. `test_rules.py` 의
> `TestWhyThisSpikeExists` 가 이 사실을 테스트로 박아둔 것입니다.

### Q3 — 닫기

- [x] `--action close` 로 실행하고 쇼츠를 연다 → **탭만 닫히는가, 창 전체가 닫히는가**
- [ ] 다른 탭에 작업 중이던 게 있었다면 그것도 같이 날아가는가
- [ ] 메모장에 글자를 쓰고 대상으로 삼아본다 → "저장하시겠습니까?" 대화상자가 뜨는가
- [ ] 관리자 권한으로 띄운 창에도 통하는가

> **예상 결과:** 크롬은 **창 전체가 닫힙니다.** `WM_CLOSE`는 창 단위 메시지라
> 탭이라는 개념을 모릅니다. 탭 하나만 닫으려면 브라우저 확장 + 네이티브 메시징이 필요합니다.
> 이게 확인되면 **"확장을 만들 것인가"가 다음 결정**입니다.

### 그 밖에

- [ ] 1분 이상 자리를 비워본다 → `(idle)` 표시가 붙는가
- [ ] Ctrl+C 로 끄면 앱별 사용 시간 요약이 제대로 나오는가
- [ ] `spike_log.jsonl` 을 열어본다 → 기록된 내용이 설계서의 `usage_session` 과 맞아떨어지는가

## 4. 결과에 따른 다음 갈림길

| 확인 결과 | 다음 결정 |
|---|---|
| URL이 잘 읽히고 안정적 | UI Automation으로 진행. 단 브라우저 업데이트 때 깨질 각오 |
| URL이 느리거나 자주 실패 | 브라우저 확장 + 네이티브 메시징으로 전환 (작업량 +1주, 대신 탭 단위 제어까지 얻음) |
| URL을 아예 못 읽음 | 대표 기능을 **"크롬 전체 사용 시간 경고"** 로 낮추거나, 확장 필수로 확정 |
| 창 전체가 닫힘 (예상됨) | `close`는 데스크톱 앱에만 쓰고, 브라우저는 `warn`/`delay`로. 또는 확장 도입 |

## 5. 코드 구조 (읽는 순서)

```
watch.py
├─ WindowInfo          지금 창의 모습 (title / exe / url / hwnd)
│
├─ [OS 의존]  갈아끼울 수 있게 분리한 부분
│   ├─ WindowsProbe    ctypes로 Win32 API 직접 호출
│   │   ├─ probe()            창 제목 + 프로세스명
│   │   ├─ _browser_url()      ★ UIAutomation으로 주소창 읽기
│   │   ├─ idle_seconds()     GetLastInputInfo
│   │   └─ close_window()     ★ WM_CLOSE 전송
│   └─ SimulatedProbe  가짜 시나리오 재생 (OS 없이 로직 검증)
│
└─ [로직]  OS 없이도 테스트되는 부분
    ├─ Rule / Condition       ← 설계서의 block_rule / rule_condition 과 같은 모양
    ├─ rule_matches()         같은 group_no는 OR, 다른 group_no는 AND
    ├─ pick_rule()            priority 낮은 것 우선
    └─ SessionTracker         ← 설계서의 usage_session 과 같은 모양
```

**이 분리가 이 스파이크에서 가장 배울 만한 부분입니다.** OS에 붙는 코드는
테스트하기 어렵고 Windows에서만 돌지만, 규칙 판정과 세션 집계는 순수 함수라
`test_rules.py` 로 어디서든 검증됩니다. 나중에 macOS를 지원하게 되면
`MacProbe` 클래스 하나만 추가하면 됩니다.

그리고 `Rule`/`Condition`/`Session` 이 DB 설계의 테이블과 같은 모양이라는 점도
의도적입니다. 스파이크가 끝나면 이 자료구조를 그대로 SQLite에서 읽어오게 바꾸면 됩니다.

## 6. 아직 안 한 것 (일부러)

DB 저장, 고양이 UI, 설정 화면, 스케줄(업무시간) 조건, 크로스플랫폼, 예외 처리.
전부 Q1~Q3의 답이 나온 뒤에 할 일입니다. **스파이크에 기능을 더하고 싶어지면
그건 스파이크가 끝났다는 신호입니다** — 결과를 적어두고 이 폴더는 버리세요.
